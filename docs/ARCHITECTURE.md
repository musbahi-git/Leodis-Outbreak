# Architecture

## Goal of this stage

Ship a small, polished, demonstrable app quickly while leaving clean seams for the real
backend, the real map and real location. Everything below is in the repository today.

## Layers

```
UI (UI Toolkit)            Bootstrap.uxml / Bootstrap.uss / RadarView / ScreenSwitcher
        │  reads SessionView, sends intents (start / end / reset)
GameApp (MonoBehaviour)    owns one IGameBackend, ticks it, renders SessionView
        │
IGameBackend               interface: StartSession, EndSession, ResetToLobby, Tick, View, ViewChanged
        │
LocalDemoBackend           on-device simulation (today)
RemoteBackend              networked client of the real server (later, same interface)
```

The UI depends only on `SessionView` and `IGameBackend`. Swapping the demo for a networked
backend should not touch any UI code.

## Trust boundary

The brief requires that hidden runner coordinates are protected server-side and never sent
to hunters. The demo backend already models this:

- `LocalDemoBackend` keeps true runner positions in a private class.
- The `SessionView` it publishes contains, for runners, only the **last revealed position** and
  the session time at which it was revealed.
- Hunters are public and shown live.
- Even the synthetic hunter AI navigates using revealed positions only, so the demo behaves
  like the real game will.

The real server will own the same rule. The client must never receive data it is not allowed
to show.

## Session model

- `SessionPhase`: `Lobby → Running → Ended`.
- `SessionOutcome`: `RunnersSurvived` (timer ran out), `AllRunnersCaptured`, `Aborted`.
- Capture rule: a hunter within `CaptureRadiusMetres` of a runner's true position captures the
  runner; the runner's role flips to `Hunter` (from the brief).
- Reveals: every `RevealIntervalSeconds` the server publishes the position of every free runner.
  The first reveal is published at session start.
- Positions are local metres relative to a play-area origin (x east, y north). When real
  geolocation arrives, a projection from latitude/longitude to this local frame will be added
  on the backend side; the UI contract stays the same.

## Scene

`Assets/_Project/Scenes/Bootstrap.unity` is generated by `Leodis > Setup > Rebuild Bootstrap Scene`:

- `Main Camera` — orthographic, solid colour `#0B1320`.
- `EventSystem` + `InputSystemUIInputModule` (project uses the Input System package only).
- `App` — `UIDocument` (Bootstrap.uxml + `LeodisPanelSettings`, 1080×1920 scale-with-screen-size)
  and `GameApp`.

Because the scene is produced from code, nothing depends on hand-made Inspector wiring and the
set-up is reproducible on any machine or in the cloud.

## UI

- UI Toolkit was chosen over uGUI because its layout and styling live in text files (UXML/USS)
  that are diffable and can be authored and reviewed without the Inspector.
- Styling uses USS custom properties for colours and USS transitions for screen changes and
  button presses.
- `RadarView` draws the play area with `Painter2D` (vector API). Runners appear at their last
  reveal with a ring that grows and fades until the next reveal, hunters as diamonds, the local
  player with a halo. This is the readable placeholder for the 3D map.
- Safe-area insets are applied to the `safe-area` element from `Screen.safeArea`.

## Assemblies

- `LeodisOutbreak.Runtime` — ships in builds. No editor code.
- `LeodisOutbreak.Editor` — editor only (scene builder, validation). References Runtime,
  `Unity.InputSystem`, `UnityEngine.UI` (for `EventSystem`).

## Deliberately not here yet

Authentication, networking, real location, background tracking, AR, Cesium/3D map, backend
service. See `docs/ROADMAP.md`.
